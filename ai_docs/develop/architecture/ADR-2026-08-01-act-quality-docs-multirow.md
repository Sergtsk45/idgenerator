# ADR: Несколько документов качества на материал в акте (D′)

**Дата:** 2026-08-01  
**Статус:** Accepted  
**План:** `ai_docs/develop/plans/2026-08-01-act-quality-doc-instances.md`

## Контекст

В реестре у одного материала может быть много документов качества (паспорта, сертификаты) и опционально партия. Партия **не связывает и не ограничивает** выбор документов для акта. Нужно включать в акт несколько docs одного материала (например, два паспорта термометра).

## Решение

1. **Модель D′:** несколько строк `task_materials` / `act_material_usages` с одним `projectMaterialId` и разными `qualityDocumentId`. `batchId` — optional, ортогонален.
2. **Unique:** `(task_id, project_material_id, quality_document_id)`; `batch_id` вне unique. Дубль одного doc в задаче запрещён.
3. **П.3 АОСР:** groupBy материал → перечень docs в одной фразе/ячейке:  
   `термометр БиТ-63 паспорт зав. №0091, паспорт зав. №0096`.
4. **Приложения:** отдельные PDF на каждый выбранный `documentId` (`act_document_attachments`).
5. **Выбор:** multi-select docs при добавлении материала в график; правка приложений в карточке акта.
6. **`acts.attachments_manual`:** после ручной правки приложений `generate-acts` не затирает `act_document_attachments` до явного сброса.
7. **Без PDF:** выбор разрешён; в карточке акта клик по строке → upload файла на `documentId`.

## Последствия

- Миграция unique index на `task_materials` и колонка `attachments_manual` на `acts`.
- UI `SelectTaskMaterials` и `ActDetail` усложняются (multi-select, редактор приложений).
- Текст п.3 меняет формат с нумерованного списка на сгруппированный перечень.

## Отклонённые альтернативы

- Экземпляр = партия + паспорт 1:1 — противоречит домену (партия ⟂ docs).
- B′ multi-value на одной строке — больше схемы при том же UX результате для MVP.
- Только редактор приложений в акте без multi-row в задаче — п.3 хуже стыкуется с комплектацией на графике.
