# Промпт для агента-дебагера: баги UI графика Ганта (idgenerator)

**Контекст**: объект «Росреестр Забурхановская 100», schedule id=7, sourceType=`works`, ~128 позиций ВОР (2 коллекции: УзелУправления + Автоматика).  
**Окружение**: prod https://idgenerator.duckdns.org, код: `~/projects/idgenerator`.  
**Не чинить вслепую** — сначала подтвердить гипотезы тестами/репро, затем патч.

Пользователь наблюдает две связанные проблемы в UI `/schedule`.

---

## Проблема 1 — расхождение наименований строк и таймлайна (вертикальный сдвиг баров)

### Симптомы (как видит пользователь)
1. Наименование работы в левой колонке не соответствует полоске задачи (бару) справа на той же визуальной высоте.
2. При большом числе задач сдвиг накапливается — внизу графика рассинхрон особенно заметен.

### Где смотреть в коде
- `client/src/pages/Schedule.tsx`
  - левая колонка: `filteredTasks.map(...)` (~стр. 1294+), высота строки `rowHeight = 88`, подстроки `auxRowHeight = 32`;
  - расчёт вертикальных координат баров: `scheduleRowLayout` (~стр. 465–490), бары ~стр. 1561–1605;
  - фон сетки таймлайна: `repeating-linear-gradient(... transparent ${rowHeight}px)` — **только 88px**, без учёта раскрытых aux-строк.

### Гипотезы (проверить по приоритету)
1. **H1 (высокая)**: `scheduleRowLayout` строится по массиву `tasks`, а отрисовка левой колонки и баров — по `filteredTasks`. При фильтре `with-act` / `without-act` индексы/`top` считаются так, будто присутствуют все задачи → бары съезжают относительно подписей.
2. **H2 (высокая)**: при раскрытии подстрок (`expandedTaskIds`) суммарная высота растёт (`rowHeight + auxCount * auxRowHeight`), но сетка таймлайна продолжает рисоваться шагом `rowHeight` → визуальный «съезд» относительно линий сетки; при ошибке в подсчёте auxCount для части задач — и реальный рассинхрон left/right.
3. **H3 (средняя)**: в графике сейчас **и** задачи на auxiliary-позициях, **и** раскрываемые aux-блоки под main (см. проблему 2). Раскрытие main сдвигает все следующие бары на `N * 32px`, а слева дублируются те же позиции как отдельные 88px-строки → накопленный сдвиг к низу списка.
4. **H4 (низкая)**: рассинхрон скролла двух панелей (если left/right в разных scroll-контейнерах) — проверить DOM.

### Как репродьюсить
1. Открыть `/schedule` на объекте с 100+ задачами (works).
2. Без фильтра: проскроллить вниз, сравнить код/название слева с баром справа на одной горизонтали.
3. Включить фильтр «с актом» / «без акта» — проверить, усиливается ли сдвиг.
4. Раскрыть несколько строк с подстроками — проверить, растёт ли рассинхрон.

### Критерий исправления
- Для любого фильтра и любого набора `expandedTaskIds`: i-я подпись слева и бар задачи с тем же `task.id` имеют одинаковый `top` (допуск 1px).
- Сетка таймлайна либо совпадает с фактическими границами строк (включая aux), либо не претендует на построчное выравнивание.
- Добавить regression-тест/story на рассинхрон `tasks` vs `filteredTasks` в layout.

## Проблема 2 — подстроки материалов не под своими основными строками; порядок «сломался»

### Симптомы (как видит пользователь)
1. После строки `1` сразу идёт строка `10` (а не `2`).
2. У строки `10` в подстроках оказываются `40.2` и `40.3` (чужие материалы).
3. Строки `2, 3, 4, 5, 6…` «растеряны» по графику.
4. Некоторые дробные коды (`54.1`, `55.1`) отображаются как **самостоятельные** строки Ганта, а не как подстроки родителей `54` / `55`.

### Подтверждённые факты по данным prod (API)
- В `works` **два набора** с **пересекающимися `orderIndex`** (0…61 дважды — две коллекции ВОР).
- Пример коллизии: при `orderIndex === 10` одновременно есть `code=10` (main) и `code=40.2` (aux).
- `compareWorksOrder` сначала сравнивает `orderIndex`, затем code → при обходе для группировки `40.2` оказывается **сразу после** `10` и цепляется к нему.
- В schedule сейчас **128 tasks**, из них **64 на auxiliary works** (`10.1`, `54.1` и т.д. как отдельные задачи). Актуальный код bootstrap (`storage.bootstrapScheduleTasksFromWorks`) уже фильтрует `isMainWorkPosition` и умеет удалять legacy aux-tasks — но на этом объекте график, похоже, **не пересобран** после фикса / либо в UI всё ещё смешаны оба слоя.

### Где смотреть в коде
- `shared/workPositionKind.ts` — `isMainWorkPosition`, `groupAuxiliaryWorksByMainId`, `compareWorksOrder`.
- `client/src/pages/Schedule.tsx` — `sortedWorks`, `auxiliaryWorksByMainId`, раскрытие aux в левой колонке.
- `server/storage.ts` — `bootstrapScheduleTasksFromWorks` (filter main + delete auxiliaryTaskIds).
- Импорт ВОР / двух коллекций: как выставляется `orderIndex` (должен быть **глобально уникальным** в рамках объекта, а не с нуля в каждой коллекции).

### Гипотезы
1. **H1 (подтверждена данными)**: коллизии `orderIndex` между коллекциями ломают `groupAuxiliaryWorksByMainId` (порядок обхода ≠ иерархия кодов) → под `10` попадают `40.2`/`40.3`.
2. **H2 (подтверждена данными)**: в Ганте остаются schedule_tasks на auxiliary works → `54.1`/`55.1` видны как самостоятельные строки; одновременно UI показывает их ещё и как expandable subrows у main.
3. **H3**: bootstrap/`orderBy(asc(orderIndex), asc(code))` при равных orderIndex даёт лексикографический/смешанный порядок (`1`, `10`, `2`…), а не натуральный порядок кодов внутри объекта.
4. **H4**: группировка идёт «по последнему main в линейном обходе», а не по префиксу кода (`40.2` → parent `40`). При битом порядке обхода это фатально.

### Как репродьюсить
1. `GET /api/works` → сгруппировать по `orderIndex`, найти дубликаты (ожидаются пары вроде `10`+`40.2`).
2. `GET /api/schedules/7` → посчитать tasks, у которых `isMainWorkPosition(work)=false` (ожидается >0 на текущем объекте).
3. В UI: раскрыть строку `10` — увидеть чужие подстроки; найти `54.1` как отдельную строку.
4. Unit: расширить `tests/work-position-kind.test.ts` кейсом «два списка с пересекающимся orderIndex».

### Критерий исправления
- Порядок основных строк Ганта: натуральный по коду/глобальному orderIndex: `1, 2, 3…` (не `1, 10, 11, 2`).
- Под строкой `N` только подстроки `N.1`, `N.2`, … (никогда `40.2` под `10`).
- В `schedule_tasks` только main-позиции; auxiliary только в UI как nested rows (или явная отдельная модель), без дублей.
- `orderIndex` в `works` уникален (или сортировка/группировка ключуется по `(collectionId, orderIndex)` / глобальному ключу), импорт двух ВОР не перемешивает иерархию.
- После фикса: повторный bootstrap на объекте 3 очищает 64 aux-tasks и корректно группирует подстроки.
