# Task Tracker: безопасный вынос `routes-refactor` без `feature/tablet-ui`

> **Цель**: получить чистую интеграционную ветку без нежелательного дизайна из `feature/tablet-ui`, но с сохранением модульного рефактора маршрутов.
>
> **Ключевой факт**: `origin/main` уже содержит `feature/tablet-ui`, а `origin/refactor/routes-modularization` построена поверх нее. Поэтому обычный merge не подходит.

> **Рекомендуемый подход**: не чинить текущую историю, а собрать новую чистую ветку от коммита до `feature/tablet-ui`, затем выборочно перенести только нужные коммиты.

## Стратегия

### Вариант A — рекомендуемый

Собрать новую ветку вручную:

1. стартовать от `7e5dbc8`;
2. перенести только pure routes commits;
3. отдельно решить, какие старые ветки потом подтягивать;
4. не тащить `feature/tablet-ui` и связанный UI-код.

**Плюсы**:
- самый чистый результат;
- нет наследования нежелательного дизайна;
- проще контролировать состав изменений.

**Минусы**:
- придется руками разруливать конфликты;
- возможны дополнительные правки для совместимости.

### Вариант B — быстрый, но рискованный

Оставить текущий `main` и делать `revert` всего дизайна из `feature/tablet-ui`.

**Плюсы**:
- история остается линейной;
- не нужно собирать новую ветку с нуля.

**Минусы**:
- высокий риск сломать UI и часть сопутствующих изменений;
- трудно отделить дизайн от прочих полезных правок;
- будет много шумных обратных коммитов.

### Вариант C — ручной перенос по файлам

Не cherry-pick коммиты, а вручную переносить только серверные файлы `server/routes.ts` и `server/routes/*`.

**Плюсы**:
- максимальный контроль;
- можно адаптировать код к более старой базе без привязки к старой истории.

**Минусы**:
- выше риск случайно потерять поведение;
- больше ручной работы;
- хуже трассируется происхождение изменений.

## Рекомендуемый пошаговый план

## Этап 0. Зафиксировать текущее состояние

- **Цель**: ничего не потерять перед восстановительными работами.
- **Статус**: к выполнению

### Шаги

1. Проверить текущую ветку и наличие незакоммиченных изменений:

```bash
git status
git rev-parse --abbrev-ref HEAD
```

2. Если в рабочем дереве есть незавершенные изменения, не трогать их в этой же папке.

3. Создать отдельный `worktree`, чтобы не мешать текущей работе:

```bash
git worktree add ../TelegramJurnalRabot-routes-rebuild 7e5dbc8
```

4. Перейти в новый `worktree` и создать рабочую ветку:

```bash
cd ../TelegramJurnalRabot-routes-rebuild
git checkout -b rebuild/routes-without-tablet-ui
```

### Критерий готовности

- текущая рабочая папка не затронута;
- новая ветка создана от коммита до `feature/tablet-ui`.

## Этап 2. Перенести только pure routes commits

- **Цель**: забрать модульный рефактор маршрутов без UI-дизайна.

### Шаги

1. Переносить коммиты по одному и после каждого проверять статус:


2. После каждого конфликта:

```bash

```

3. Разрешать конфликты вручную, затем:

```bash
git add <исправленные-файлы>
git cherry-pick --continue
```

## Основные риски

### Риск 1. Конфликты в `server/routes.ts`

**Вероятность**: высокая  
**Последствие**: ручная стыковка диспетчера и auth registration logic

**Снижение риска**:
- переносить коммиты по одному;
- после каждого проверять итоговый файл вручную.

### Риск 2. Скрытые зависимости на код из веток после `tablet-ui`

**Вероятность**: средняя  
**Последствие**: битые импорты, несовместимые типы, missing helpers

**Снижение риска**:
- не брать поздние коммиты;
- руками проверять imports/exports в серверных модулях.

### Риск 3. Runtime-регрессии без ошибок компиляции

**Вероятность**: средняя  
**Последствие**: endpoint компилируется, но меняет поведение

**Снижение риска**:
- прогнать smoke всех доменов;
- отдельно проверить auth, acts, schedule, materials.

### Риск 4. Повторное затаскивание дизайна через другие ветки

**Вероятность**: высокая  
**Последствие**: нежелательный UI вернется в новую ветку незаметно

**Снижение риска**:
- после восстановления не merge-ить старые ветки автоматически;
- перед каждым переносом делать `git diff --name-status`.

## Неблагоприятные последствия, если сделать неаккуратно

- можно получить чистую историю, но сломанный API;
- можно случайно потерять часть бизнес-логики вместе с поздними коммитами;
- можно вернуть `feature/tablet-ui` через косвенный merge другой ветки;
- можно получить долгую серию конфликтов в будущем, если старые ветки продолжат жить параллельно.
