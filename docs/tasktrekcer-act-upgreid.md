## Контекст для агента

### Проблема

На проде в акте `id=21` (Акт №5) материал «Кран шаровой LD КШЦф 080/070/016 NP02» имеет корректно привязанный паспорт:

| Проверка | Факт (прод, 2026-07-31) |
|----------|-------------------------|
| `act_material_usages` | 1 запись, `qualityDocumentId = 61` |
| `act_document_attachments` | 1 запись, `documentId = 61` |
| `documents.fileUrl` | `/api/documents/files/6/61_passport_LD_KShTsF_080070016_NP02_batch_1809162_cc414dcd.pdf` |
| Файл | `200 OK`, `application/pdf`, `%PDF-`, ~5.5 МБ |

Привязка данных работает. Отсутствует именно **сборка файлов приложений**: `generateAosrPdf` пишет в PDF только текстовые строки (`buildAttachmentsText`), сами файлы никуда не подкладываются.

### Решение

Разделить экспорт на две независимые операции:

1. **Экспорт акта** — существующее поведение (АОСР по шаблону, приложения только текстом).
2. **Экспорт приложений** — новый отдельный PDF: титульная страница + постранично вшитые файлы документов из `act_document_attachments`.

Реестр приложений в пакете **не нужен** (решение от 2026-07-31): после титульной страницы сразу идут страницы документов.

### Ключевые файлы

| Файл | Роль в задаче |
|------|---------------|
| `server/routes/acts.ts` | текущий `POST /api/acts/:id/export`, раздача `/api/pdfs/:filename` — рядом добавляется новый эндпоинт |
| `server/pdfGenerator.ts` | pdfmake + шрифты с кириллицей (Roboto/Times), `buildAttachmentsText` |
| `server/document-files.ts` | `resolveDocumentFile`, `isPdf`, `documentsUploadRoot` — безопасное чтение файлов из хранилища |
| `server/storage.ts` | `getActDocAttachments(actId)` — источник списка приложений |
| `shared/routes.ts` | контракт API (`api.acts.*`), Zod-схемы |
| `client/src/pages/ActDetail.tsx` | UI экспорта (кнопка + Sheet выбора шаблона) |
| `client/src/lib/pdf-download.ts` | `openPdfDownload` — скачивание в браузере и Telegram MiniApp |

---

## Цель

Дать пользователю возможность выгрузить официальный комплект приложений к акту одним PDF-файлом, не смешивая его с самим АОСР.

---

## Состав PDF приложений

1. **Титульная страница**
   - «Приложения к Акту №{actNumber}»
   - наименование объекта
   - дата акта (`dateEnd`)
   - количество документов
2. **Страницы документов** — последовательно, по `orderIndex`, без разделителей-реестра.

Имя файла для пользователя: `Акт_{actNumber}_приложения.pdf`.

---

## API

```http
POST /api/acts/:id/export-attachments
```

Ответ `200`:

```json
{
  "url": "/api/pdfs/act_attachments_21_1785288000000.pdf",
  "filename": "Акт_5_приложения.pdf",
  "documentsCount": 1
}
```

Ошибки:

| Код | Причина | Тело |
|-----|---------|------|
| `400` | некорректный `id` | `{ "message": "Invalid act id" }` |
| `401` | нет авторизации | `{ "error": "..." }` |
| `404` | акт не найден или не принадлежит текущему объекту | `{ "message": "Act not found" }` |
| `409` | нет приложений | `{ "message": "Нет документов для экспорта" }` |
| `422` | файлы отсутствуют/повреждены | `{ "message": "...", "problems": [{ "documentId": 61, "title": "...", "reason": "missing\|not_pdf\|unreadable" }] }` |

Источник документов — **только** `act_document_attachments` данного акта (не все документы материала, не bindings).

## Технические требования

- Слияние PDF — через `pdf-lib` (в проекте пока нет ни одной библиотеки слияния; `pdfmake` умеет только генерировать).
- Титульную страницу генерировать существующим `pdfmake`-пайплайном (там уже подключены шрифты с кириллицей), затем сливать с документами через `pdf-lib`. Не тянуть `@pdf-lib/fontkit` ради одной страницы.
- Читать файлы только через `resolveDocumentFile(objectId, filename)` — защита от path traversal уже реализована там.
- **Не** загружать внешние `http(s)`-ссылки на сервере (SSRF). В v1 поддерживается только внутренний путь `/api/documents/files/:objectId/:filename`; внешние URL попадают в `problems` с `reason: "unsupported_url"`.
- Дедуплицировать по `documentId`.
- Лимиты: не более 100 документов и не более 200 МБ суммарно на один пакет; при превышении — `422` с понятным сообщением.
- Неполный официальный комплект молча не отдавать: любая проблема с файлом → ошибка со списком, а не PDF без страниц.
- Исходные файлы документов не изменять и не перезаписывать.
- Готовый пакет писать в `generated_pdfs/` и отдавать через существующий `GET /api/pdfs/:filename`.
- Эндпоинт защитить `appAuth` и проверкой принадлежности акта текущему объекту (как в `GET /api/acts/:id`).

## Acceptance criteria

- [ ] На странице акта две кнопки: «Экспорт акта» и «Экспорт приложений».
- [ ] «Экспорт акта» не содержит страниц файлов приложений (поведение как сейчас).
- [ ] «Экспорт приложений» отдаёт отдельный PDF: титульная страница, затем страницы документов.
- [ ] Реестра приложений в пакете нет.
- [ ] Порядок документов соответствует `orderIndex` в `act_document_attachments`.
- [ ] Для акта №5 в пакете присутствуют страницы паспорта крана шарового (документ `id=61`).
- [ ] Акт без приложений: кнопка недоступна, API отвечает `409`.
- [ ] Повреждённый/отсутствующий файл: `422` со списком проблемных документов, пакет не выдаётся.
- [ ] Внешние `http(s)` URL сервером не запрашиваются.
- [ ] Исходные файлы документов после экспорта не изменены.
- [ ] Эндпоинт недоступен без авторизации и для актов чужого объекта.
- [ ] Скачивание работает в браузере и Telegram MiniApp.
