# Первый MVP: AI-инженер исполнительной документации

## 1. Назначение

Первый MVP должен доказать, что пользователь может пройти в одном диалоге следующий путь:

```text
Смета
→ анализ
→ запрос недостающих данных
→ черновой график
→ подтверждение графика
→ реестр материалов и оборудования
→ запрос сертификатов/паспортов
→ проверка комплектности
→ черновики актов
→ журнал работ
→ комплект файлов для проверки
```

MVP не обязан полностью заменять инженера ПТО. Его задача — создать контролируемый, воспроизводимый и проверяемый процесс подготовки исходных данных и черновиков исполнительной документации.

## 2. Роли

### Пользователь

- загружает смету;
- отвечает на уточняющие вопросы;
- подтверждает принятые допущения;
- загружает сертификаты, паспорта и другие документы;
- подтверждает график и выпуск документов.

### AI-агент

- ведёт диалог;
- вызывает MCP-инструменты;
- интерпретирует структурированные ответы MCP;
- задаёт только те вопросы, которые вернул механизм `missing inputs`;
- не выдумывает нормативы, даты, производительность и ответственных лиц;
- показывает допущения до подтверждения;
- не выполняет опасные изменения без согласия пользователя.

### MCP-IDgenerator

- аутентифицирует пользователя;
- принимает ссылки/идентификаторы загруженных файлов;
- создаёт и хранит состояние workflow;
- импортирует и анализирует смету;
- рассчитывает черновой график по формальным правилам;
- ведёт реестр материалов и документов;
- проверяет готовность актов;
- вызывает существующую генерацию PDF;
- формирует машинно-читаемый статус следующего шага.

## 3. Границы MVP

### В MVP входит

1. Один активный объект на один workflow.
2. Одна импортированная смета как источник графика.
3. Excel-формат, уже поддерживаемый текущим импортом смет.
4. Два режима планирования:
   - по целевому сроку;
   - по численности бригады, только если в смете есть пригодная трудоёмкость.
5. Линейный график по порядку основных позиций сметы.
6. Рабочий календарь: 5/2 или 6/1, одна смена.
7. Черновой реестр материалов и оборудования.
8. Минимальная матрица требований к документам:
   - `material` → сертификат/декларация/паспорт качества;
   - `equipment` → паспорт;
   - `product` → сертификат или паспорт согласно правилу.
9. Загрузка и привязка PDF-документов к материалам.
10. Проверка комплектности.
11. Создание актов из утверждённого графика существующим механизмом.
12. Формирование чернового журнала работ на основе графика, актов и сообщений.
13. Итоговый manifest со списком готовых и отсутствующих документов.
14. Все финальные действия выполняются после подтверждения пользователя.

### В MVP не входит

- автоматический поиск и применение строительных норм из интернета;
- юридическая гарантия соответствия комплектности;
- сложная оптимизация ресурсов;
- параллельные бригады и многосменный режим;
- автоматическое распознавание произвольных PDF-смет;
- цифровая подпись;
- автоматическая отправка заказчику;
- полностью автономный выпуск документов без проверки человеком;
- полный состав всех разделов общего журнала работ по каждой возможной нормативной форме.

## 4. Сквозной сценарий

### Этап 1. Создание workflow

Пользователь прикладывает смету и пишет:

> Подготовь график и исполнительную документацию по этому объекту.

Агент вызывает:

```text
create_execution_workflow
create_upload_session
import_estimate_from_upload
```

MCP создаёт workflow и возвращает:

```json
{
  "workflowId": "wf_...",
  "stage": "estimate_imported",
  "nextAction": "analyze_estimate"
}
```

### Этап 2. Анализ сметы

Агент вызывает:

```text
analyze_estimate
```

MCP определяет:

- основные работы;
- разделы;
- объёмы;
- ресурсы;
- наличие трудозатрат;
- материалы;
- оборудование;
- предупреждения импорта.

Ответ должен быть структурированным:

```json
{
  "stage": "awaiting_schedule_inputs",
  "summary": {
    "mainWorks": 48,
    "materials": 126,
    "equipment": 8,
    "laborHoursAvailable": true
  },
  "missingInputs": [
    {
      "key": "projectStartDate",
      "type": "date",
      "question": "Когда должны начаться работы?",
      "required": true
    },
    {
      "key": "workingCalendar",
      "type": "enum",
      "options": ["5x2", "6x1"],
      "question": "Какой рабочий календарь использовать?",
      "required": true
    },
    {
      "key": "planningMode",
      "type": "enum",
      "options": ["target_duration", "crew_size"],
      "question": "Что известно точнее: срок выполнения или численность бригады?",
      "required": true
    }
  ]
}
```

### Этап 3. Уточнение параметров

Агент задаёт вопросы по одному или компактными логическими группами. Каждый ответ сохраняется через:

```text
set_workflow_input
```

MCP всегда возвращает актуальное состояние:

```json
{
  "stage": "awaiting_schedule_inputs",
  "remainingInputs": [...]
}
```

Правила:

- не спрашивать повторно сохранённые данные;
- при изменении входного параметра помечать зависимые расчёты устаревшими;
- хранить источник каждого значения: `user`, `estimate`, `system_default`, `calculated`;
- системные defaults должны быть явно показаны и подтверждены.

### Этап 4. Черновой график

После заполнения обязательных параметров агент вызывает:

```text
calculate_schedule_draft
```

#### Режим `target_duration`

Пользователь задаёт общий срок. Продолжительность работ распределяется пропорционально весам:

1. трудоёмкость позиции, если доступна;
2. иначе стоимость труда/машин, если значение пригодно;
3. иначе объём позиции;
4. иначе равный вес с предупреждением.

#### Режим `crew_size`

Поддерживается только при наличии трудоёмкости:

```text
durationDays =
ceil(laborHours / (crewSize × shiftHours × utilizationFactor))
```

Для MVP:

- `shiftHours` по умолчанию 8, требуется подтверждение;
- `utilizationFactor` по умолчанию 0.85, требуется подтверждение;
- работы идут последовательно по `orderIndex`;
- нерабочие дни пропускаются;
- минимальная длительность позиции — 1 рабочий день.

Если трудоёмкости нет, MCP не должен считать срок по числу людей. Он возвращает `needs_input` и предлагает режим целевого срока либо ручные длительности групп.

### Этап 5. Подтверждение графика

Агент показывает:

- начало и окончание;
- общий срок;
- принятые допущения;
- позиции с низкой уверенностью;
- предупреждения.

До подтверждения график имеет статус `draft`.

После явного согласия:

```text
approve_schedule
```

MCP фиксирует версию и создаёт/обновляет `schedule_tasks`.

### Этап 6. Реестр материалов

Агент вызывает:

```text
build_material_register
```

MCP:

- извлекает ресурсы;
- классифицирует их;
- объединяет дубликаты по нормализованному имени и единице;
- сохраняет связь с позициями сметы и задачами графика;
- создаёт `project_materials` при необходимости;
- определяет требуемые типы документов.

Агент показывает пользователю:

- материалы;
- оборудование;
- количество;
- связанные работы;
- требуемые документы;
- неоднозначные классификации.

Неоднозначные позиции пользователь подтверждает или исправляет.

### Этап 7. Запрос документов

Агент вызывает:

```text
get_missing_quality_documents
```

MCP возвращает перечень отсутствующих документов с причиной:

```json
{
  "missing": [
    {
      "materialId": 42,
      "name": "Насос циркуляционный",
      "requiredDocTypes": ["passport"],
      "usedInTaskIds": [101, 102],
      "blockingActNumbers": [4]
    }
  ]
}
```

Пользователь загружает PDF. Агент создаёт upload session и вызывает:

```text
attach_document_from_upload
```

MCP:

- проверяет формат и размер;
- создаёт запись `documents`;
- сохраняет файл;
- создаёт `document_bindings`;
- обновляет готовность.

### Этап 8. Акты

После утверждения графика агент вызывает:

```text
check_acts_readiness
```

MCP проверяет:

- номер акта;
- шаблон;
- даты;
- работы;
- материалы;
- документы качества;
- проектную документацию;
- нормативные ссылки;
- исполнительные схемы;
- исходные данные сторон и представителей.

Агент запрашивает только блокирующие сведения.

После подтверждения:

```text
generate_acts
export_act_pdf
export_act_attachments
```

На первом MVP допускается создание черновиков со статусом `draft`, если бизнес-поля заполнены не полностью, но финальный пакет должен блокироваться.

### Этап 9. Журнал работ

MCP формирует черновой журнал:

```text
generate_worklog_draft
```

Источники:

- утверждённый график;
- сформированные акты;
- сообщения о фактически выполненных работах.

Плановые записи нельзя выдавать за фактические. Каждая строка содержит `sourceType` и статус `planned`/`reported`/`act_confirmed`.

### Этап 10. Итоговый пакет

Агент вызывает:

```text
check_handover_readiness
build_execution_package
```

Пакет содержит:

- manifest JSON/PDF;
- утверждённый график;
- акты;
- приложения;
- черновой журнал;
- список отсутствующих документов;
- список использованных допущений;
- журнал действий.

## 5. Состояния workflow

```text
created
estimate_upload_pending
estimate_imported
estimate_analysis_ready
awaiting_schedule_inputs
schedule_draft_ready
schedule_approved
materials_register_ready
awaiting_quality_documents
acts_blocked
acts_ready
acts_generated
worklog_draft_ready
package_ready
completed
failed
```

Каждый переход должен быть детерминированным и сохраняться в БД.

## 6. Контракт ответа MCP

Каждый orchestration-инструмент возвращает общий envelope:

```json
{
  "workflowId": "wf_...",
  "stage": "awaiting_quality_documents",
  "status": "ok",
  "summary": "Краткое описание результата",
  "data": {},
  "warnings": [],
  "missingInputs": [],
  "blockingIssues": [],
  "nextActions": [
    {
      "tool": "get_missing_quality_documents",
      "reason": "Проверить комплектность"
    }
  ]
}
```

Ошибки должны быть машинно-читаемыми:

```json
{
  "status": "error",
  "error": {
    "code": "ESTIMATE_LABOR_DATA_MISSING",
    "message": "Невозможно рассчитать срок по численности без трудоёмкости",
    "recoverable": true
  }
}
```

## 7. Критерии успеха MVP

MVP считается успешным, если тестовый пользователь способен:

1. загрузить поддерживаемую смету через чат;
2. получить корректный список недостающих параметров;
3. сформировать и подтвердить график;
4. получить реестр материалов и оборудования;
5. увидеть отсутствующие сертификаты и паспорта;
6. загрузить документы и связать их с материалами;
7. сформировать хотя бы один акт и пакет приложений;
8. получить черновой журнал и manifest;
9. продолжить workflow после перезапуска чата;
10. просмотреть, какие данные были введены человеком, извлечены из сметы или рассчитаны системой.
