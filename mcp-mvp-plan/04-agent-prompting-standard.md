# Стандарт заданий для кодового агента

## 1. Назначение

Каждый файл `TASK-*.md` является самостоятельным техническим заданием, похожим на хорошо оформленный GitHub Issue. Он должен позволять агенту изучить код, составить план, реализовать изменение, запустить проверки и отчитаться доказуемым результатом.

## 2. Обязательная структура задания

1. **Роль** — кем выступает агент.
2. **Цель** — один проверяемый результат.
3. **Контекст** — зачем изменение нужно.
4. **Связанные файлы** — стартовые точки, а не исчерпывающий список.
5. **Первое действие** — изучить инструкции, код и тесты, затем кратко описать план.
6. **Scope** — что обязательно сделать.
7. **Non-goals** — что запрещено расширять.
8. **Контракты** — API, схемы, ошибки, состояния.
9. **Безопасность** — ownership, auth, limits, idempotency.
10. **Acceptance criteria** — измеримые условия.
11. **Проверки** — команды и тестовые сценарии.
12. **Формат отчёта** — изменённые файлы, решения, результаты тестов, риски.

## 3. Правила формулировки

- Один prompt — одна крупная задача.
- Использовать конкретные глаголы: «добавь», «вынеси», «проверь», «создай тест».
- Не писать «сделай красиво», «улучши всё», «оптимизируй архитектуру».
- Указывать non-goals.
- Не диктовать мелкие детали реализации, если важен результат, но фиксировать обязательные контракты.
- Просить сначала изучить существующую реализацию и переиспользовать её.
- Требовать тесты и фактические результаты команд.
- Требовать остановиться и сообщить, если обнаружено противоречие в данных, миграциях или безопасности.
- Не просить раскрывать скрытую цепочку рассуждений. Достаточно краткого плана, решений и доказательств.
- Не разрешать агенту выдумывать отсутствующие схемы, endpoints или бизнес-правила.
- Для рискованных операций требовать отдельное подтверждение.

## 4. Рабочий цикл агента

```text
Inspect
→ Plan
→ Implement smallest coherent change
→ Test
→ Review diff
→ Fix failures
→ Report evidence
```

## 5. Обязательный стартовый блок

Каждое задание содержит инструкцию:

> Перед изменениями прочитай все применимые `AGENTS.md`, `.cursor/rules`, документацию задачи, текущие схемы и тесты. Затем дай краткий план из 3–7 пунктов. Не начинай массовый рефакторинг до проверки существующей архитектуры.

## 6. Обязательный финальный отчёт

```text
1. Что реализовано
2. Какие файлы изменены
3. Какие архитектурные решения приняты
4. Какие миграции добавлены
5. Какие тесты добавлены
6. Результаты npm run check / npm test / npm run build
7. Известные ограничения
8. Что требует ручного smoke
```

## 7. Источники практик

- OpenAI: задачи для кодового агента лучше структурировать как GitHub Issue, начинать крупные изменения с плана и дробить работу на обозримые единицы.
- OpenAI Codex: качественная среда, `AGENTS.md`, воспроизводимые тесты и проверяемые логи повышают надёжность.
- MCP: tool-ы должны иметь явные схемы, пользовательский контроль, авторизацию и безопасную обработку данных.
