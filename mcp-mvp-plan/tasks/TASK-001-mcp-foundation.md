# TASK-001: MCP transport, auth context и базовые tool-контракты

## Метаданные

- **Тип:** implementation task
- **Зависимости:** нет
- **Результат:** Добавить защищённый MCP endpoint с Streamable HTTP, который использует текущую JWT-аутентификацию и предоставляет базовые диагностические инструменты без изменения бизнес-данных.

## Задание агенту

### Роль

Ты — senior TypeScript backend engineer, работающий в существующем репозитории `Sergtsk45/idgenerator`. Твоя задача — выполнить только описанный scope, сохранив совместимость существующего приложения.

### Цель

Добавить защищённый MCP endpoint с Streamable HTTP, который использует текущую JWT-аутентификацию и предоставляет базовые диагностические инструменты без изменения бизнес-данных.

### Контекст

IDgenerator уже является Express/TypeScript-приложением. MCP должен встраиваться как отдельный transport layer, а не заменять REST API.

### Связанные файлы для первичного изучения

- `package.json`
- `server/index.ts`
- `server/routes.ts`
- `server/middleware/auth.ts`
- `server/auth-service.ts`
- `server/routes/_common.ts`
- `shared/routes.ts`

Список не является исчерпывающим. Найди фактические зависимости через импорты, схемы и тесты.

### Обязательные первые действия

1. Прочитай все применимые `AGENTS.md`, `.cursor/rules`, ADR и документацию.
2. Изучи текущий код и существующие тесты; не предполагай отсутствующие контракты.
3. Дай краткий план из 3–7 пунктов.
4. Зафиксируй найденные риски и несовместимости до редактирования.
5. Не начинай широкий рефакторинг без необходимости для acceptance criteria.

### Scope

1. Добавь официальный TypeScript MCP SDK и минимально необходимые зависимости.
2. Создай `server/mcp/` и фабрику MCP server.
3. Подключи Streamable HTTP endpoint `/mcp`.
4. Реализуй получение authenticated user context из Bearer JWT.
5. Добавь tools:
   - `ping`;
   - `get_current_user`;
   - `list_objects` в read-only режиме.
6. Добавь единый builder успешного результата и MCP-ошибки.
7. Добавь structured logging без токена.
8. Добавь rate limit и ограничения размера тела для `/mcp`.
9. Документируй локальное подключение MCP-клиента.

### Non-goals

- Не реализовывать workflow.
- Не добавлять OAuth provider.
- Не открывать write-tools.
- Не переносить существующие REST routes.
- Не менять UI.

### Обязательные контракты

- `Authorization: Bearer <jwt>` обязателен для всех tools кроме transport-level initialization, если SDK требует иной handshake.
- `list_objects` возвращает только объекты текущего пользователя.
- Ошибки: `AUTH_REQUIRED`, `AUTH_INVALID`, `FORBIDDEN`, `VALIDATION_ERROR`, `INTERNAL_ERROR`.
- MCP endpoint не должен раскрывать stack trace.
- Tool names — стабильные snake_case.

### Безопасность и качество

- Всегда получать user identity из проверенного auth context.
- Не принимать доверенный `userId` из tool arguments.
- Проверять ownership всех object/workflow/entity ID.
- Для write-операций предусмотреть идемпотентность или доказать, почему она не нужна.
- Не логировать токены, содержимое секретов и полные персональные данные.
- Возвращать стабильные машинно-читаемые error codes.
- Сохранить обратную совместимость текущих REST-сценариев.
- Переиспользовать Zod и domain services вместо дублирования правил.
- Не скрывать ошибки тестов; устранить или явно описать блокер.

### Acceptance criteria

- Неавторизованный вызов не получает данные.
- JWT заблокированного пользователя отклоняется.
- Пользователь A не видит объект пользователя B.
- MCP initialization и `ping` проходят в integration test.
- REST API продолжает работать.
- Добавлена документация подключения.

### Проверки

- Unit tests для tool result/error helpers.
- Integration tests auth/no-auth.
- Ownership test для `list_objects`.
- Smoke запуск сервера и MCP handshake.

Обязательно выполнить:

```bash
npm run check
npm test
npm run build
```
