# TASK-005: Missing-input engine и формальные вопросы агенту

## Метаданные

- **Тип:** implementation task
- **Зависимости:** TASK-002, TASK-004
- **Результат:** Реализовать единый механизм, который определяет недостающие данные для текущего этапа и возвращает готовые структурированные вопросы.

## Задание агенту

### Роль

Ты — senior TypeScript backend engineer, работающий в существующем репозитории `Sergtsk45/idgenerator`. Твоя задача — выполнить только описанный scope, сохранив совместимость существующего приложения.

### Цель

Реализовать единый механизм, который определяет недостающие данные для текущего этапа и возвращает готовые структурированные вопросы.

### Контекст

Диалог не должен зависеть от догадок конкретной модели. MCP сообщает, какие поля нужны и почему.

### Связанные файлы для первичного изучения

- workflow service из TASK-002
- estimate analysis из TASK-004
- `shared/routes.ts`
- `server/mcp/tools/workflow.ts`

Список не является исчерпывающим. Найди фактические зависимости через импорты, схемы и тесты.

### Обязательные первые действия

1. Прочитай все применимые `AGENTS.md`, `.cursor/rules`, ADR и документацию.
2. Изучи текущий код и существующие тесты; не предполагай отсутствующие контракты.
3. Дай краткий план из 3–7 пунктов.
4. Зафиксируй найденные риски и несовместимости до редактирования.
5. Не начинай широкий рефакторинг без необходимости для acceptance criteria.

### Scope

1. Определи catalog workflow input definitions.
2. Для schedule stage добавь:
   - projectStartDate;
   - workingCalendar;
   - planningMode;
   - targetDurationDays или crewSize;
   - shiftHours;
   - utilizationFactor.
3. Создай dependency/conditional rules.
4. MCP `get_missing_workflow_inputs`.
5. Улучши `set_workflow_input` Zod validation.
6. Помечай calculated artifacts stale при изменении входов.
7. Возвращай вопрос, тип, options, validation и reason.
8. Поддержи подтверждение system defaults.

### Non-goals

- Не вести диалог внутри сервера.
- Не вызывать LLM.
- Не добавлять нормативные справочники.
- Не рассчитывать schedule.

### Обязательные контракты

- В crew mode без labor availability возвращать blocking issue и предлагать target duration.
- Нельзя подтвердить invalid date/negative crew.
- Default не считается подтверждённым автоматически.
- Вопросы имеют stable key.
- Не спрашивать поле повторно, если оно валидно и confirmed.

### Безопасность и качество

- Всегда получать user identity из проверенного auth context.
- Не принимать доверенный `userId` из tool arguments.
- Проверять ownership всех object/workflow/entity ID.
- Для write-операций предусмотреть идемпотентность или доказать, почему она не нужна.
- Не логировать токены, содержимое секретов и полные персональные данные.
- Возвращать стабильные машинно-читаемые error codes.
- Сохранить обратную совместимость текущих REST-сценариев.
- Переиспользовать Zod и domain services вместо дублирования правил.
- Не скрывать ошибки тестов; устранить или явно описать блокер.

### Acceptance criteria

- Для каждой комбинации planning mode возвращается правильный набор.
- Crew mode блокируется без labor data.
- Изменение start date инвалидирует schedule draft.
- API/tool не принимает неизвестные keys.
- Questions пригодны для single-select/date/number UI.

### Проверки

- Rule-engine unit matrix.
- Validation tests.
- Staleness tests.
- MCP output schema tests.

Обязательно выполнить:

```bash
npm run check
npm test
npm run build
```
